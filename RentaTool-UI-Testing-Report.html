RentaTool · UI Testing Report · Evidence date 6 October 2026

1. Executive Summary

This report summarizes the testing evidence available for RentaTool, a rental platform with a React web client, ASP.NET Core API, PostgreSQL database, Flutter mobile client, and an AI service. It focuses on user-interface behavior and the workflows connecting the web interface to the real API.

The documented isolated React test campaign reports 45 of 45 test cases passing across component/API-mocked tests, browser workflows, and selected browser non-functional checks. A separate live integration run is more mixed: 4 of 6 Playwright cases passed; claims and escrow lookups returned HTTP 500 because their database relations were missing. A Flutter catalog comparison passed, while Flutter non-functional evidence is limited.

2. Project and Test Scope

System under test

  • Web: React 18 and Vite application with login, protected operations, catalog, bookings, identity/KYC, claims, escrow, and arbitration interfaces.
  • Backend: ASP.NET Core modular API covering Identity, Catalog, Booking, and Escrow.
  • Data: PostgreSQL used for live API workflows.
  • Mobile: Flutter client. The documented live cross-platform case covers catalog only.
  • AI service: FastAPI routes are present, but no live AI-service NFR execution is recorded.

8. Defect Records and Open Work

DEF-API-ESCROW-DB — Open product defect

Affected: API-04 claims list and API-05 escrow booking lookup. Expected: claims returns 200 with an array; unknown escrow booking returns 404 (or an existing hold returns 200). Actual: both returned HTTP 500. Local diagnostic identified PostgreSQL error 42P01 for missing relations damage_claims and escrow_holds.

Likely cause: API startup calls EnsureCreated, which does not apply later migrations to an already-created database. The repository contains migration 20260915140529_AddEscrowModule. Retest: repeated in the latest run and still failed; no fix was applied. Apply the schema migration and rerun both API cases.

DEF-NFR-001 — Fixed and retested, Medium severity / High priority

Reproduction: OPTIONS /api/v1/equipment with Origin https://untrusted.invalid, requested method GET and Authorization header. The original policy echoed the untrusted origin with credentials.

Fix: API CORS now uses the explicit Cors:AllowedOrigins configuration allowlist instead of accepting every origin. Local React origins on ports 3000 and 5173 are configured; deployment origins must be set for each environment.

Retest: allowed origin http://127.0.0.1:3000 returned 204 with matching Access-Control-Allow-Origin and credentials. Untrusted origin returned 204 without either CORS allow header. Build succeeded. Evidence: nfr-testing/evidence/cors-allowlist-retest.txt; implementation in src/backend/Host/RentaTool.API/Program.cs and appsettings.json.

WEB-SEC-001 — Open dependency finding, Critical priority / P1

Actual: npm audit reported 11 dependency findings (1 critical, 6 high, 4 moderate), affecting direct packages including Vitest, Vite, Tailwind CSS and React Router DOM. Fix: not applied; remediation includes major upgrades and compatibility review. Evidence: src/web/evidence/npm-audit.json.

WEB-A11Y-001 — Fixed and retested, Medium / P2

Login notice contrast measured 3.53:1 for #6b7280 on #181c24, below the 4.5:1 normal-text expectation. Text color changed to #9ca3af. The final axe run passed the login scan.

Test harness corrections are not product defects: booking route corrected from /bookings to /bookings/tracker; Flutter screenshot setup added surface conversion; external font waiting was removed from Chromium screenshot capture.

11. Conclusion and Recommended Follow-up

The evidence demonstrates substantial web UI coverage and several complete workflows, including a real booking lifecycle and web-to-API catalog flow. The results also identify concrete backend schema and security work that should be addressed before describing all platform workflows as complete.

  1. Set the exact web/mobile deployment origins in Cors:AllowedOrigins for each deployed environment and rerun the preflight probe.
  2. Review and upgrade the vulnerable web dependency tree, then rerun audit and the affected UI/build suites.
  3. Run OWASP ZAP only after resolving the Windows security block through an approved installation source, then save its report.
  4. Collect dedicated mobile frame-performance and repeated/offline reliability evidence; M01/M02 login usability/viewport checks now pass on one Android 16 device.
  5. Add client retry and interrupted-write consistency scenarios; the current API recovery run measures process restart only.
